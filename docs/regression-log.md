# DeFi Shield 回归日志（regression-log.md）

> **这个文件是什么**：B 每次修改合约后的回归记录台账。每轮一行，倒序排列（最新在最上）。
> **配套**：缺陷详情记 `docs/issue-log.md`；本文件只记"这轮回归的结果"，不展开缺陷细节。
> **纪律**：所有数字抄自真实命令输出，并注明日志文件路径；禁止凭印象填写。

---

## 回归 SOP（收到 B 的修复通知后，照此执行）

```
□ 1. 记录版本
     git log -1 --format="%H %s"          # 记 commit hash 与提交说明
     git status --porcelain               # 必须为空（工作区干净），否则要求 B 提交完整

□ 2. 确认可编译
     npx hardhat clean && npx hardhat compile
     # 编译失败 → 停止回归，直接记 issue-log（严重度 P0：构建不可用），通知 B

□ 3. 冒烟组先行（10 秒级，主链路没坏才值得往下跑）
     npx hardhat test --grep "冒烟"
     # 冒烟红 → 记 issue-log，通知 B，本轮全量回归可以不跑（省时间）

□ 4. 定向验证（验证本轮修复的那个缺陷）
     npx hardhat test test/secure-pool.test.js --grep "<关联用例名>"
     # 用例名从 issue-log.md 对应条目的"关联测试用例"字段复制
     # 定向失败 → 缺陷未修复，issue-log 对应条目状态改回"open"，附新日志，通知 B

□ 5. 全量回归（含漏洞版对照与不变量）
     npx hardhat test 2>&1 | tee artifacts/test-output-$(date +%F-%H%M).log
     # 有失败 → 每个失败用例一条 issue-log（或更新已有条目），附最小复现命令

□ 6. 覆盖率对比
     npx hardhat coverage
     # 与上一版对比：行覆盖率下降 > 5 个百分点，必须在"遗留问题"列写明原因
     # （常见合理原因：新增教学分支；不合理原因：新代码无测试——后者记 issue）

□ 7. 记录与结论
     全绿 → 在下表记一行，结论写"通过"；
     有失败 → 记一行，结论写"不通过"，"遗留问题"列指向 issue-log 的缺陷 ID；
     只有"通过"的轮次才允许进入交付物归档（artifacts/ 日志改名留存）。
```

## 填写说明

- **触发原因**：写"修复 ISSUE-xxx"或"首次全量"或"B 重构 XX 模块"，让后人知道这轮为什么跑；
- **全量通过/失败**：抄 `npx hardhat test` 汇总行的 `passing` / `failing` 数；
- **行覆盖率(Δ)**：抄 `npx hardhat coverage` 的 % Lines，括号内写与上一轮的差值；
- **遗留问题**：写 issue-log 的缺陷 ID，多个用逗号分隔；无则写"无"；
- **结论**：只有"通过/不通过"两个值，不写"基本通过"。
